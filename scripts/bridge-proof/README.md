# Better Auth -> Supabase identity bridge proof

End-to-end proof that a standalone better-auth instance can act as the OIDC
provider Supabase Auth will trust, satisfying every acceptance criterion the
migration memory graph set before RLS activation / A9:

| Criterion | Where it is proven |
|---|---|
| issuer | `oidc-bridge.test.ts` — discovery serves the configured issuer |
| audience | id_token `aud` = registered OIDC client id; app audience configured on the JWT plugin |
| asymmetric signing key | RS256 key pair generated by the JWT plugin, verified with `jose` independently |
| kid | JWKS keys carry `kid`; the verifier selects the key by `kid` from the token header |
| JWKS discovery/rotation | `/.well-known/openid-configuration` -> `jwks_uri` -> `/jwks`; rotation test publishes a second key and both verify |
| short expiry | JWT plugin `expirationTime` (1m) + OIDC `accessTokenExpiresIn` (300s); expired tokens rejected |
| server-side session verification | `verify-token.ts` (jose: signature, issuer, audience, expiry, sub) |
| Supabase token acceptance | **proven live** on `velure-cc` — real Supabase JWTs accepted by PostgREST (`supabase-acceptance.mjs`) |
| negative tenancy tests | **proven live** on `velure-cc` — W1/W2 isolation, forged writes and moves rejected, anon denied (`supabase-acceptance.mjs`) |

Run:

```bash
pnpm exec vitest run scripts/bridge-proof/oidc-bridge.test.ts
```

## How the harness is wired (the non-obvious parts)

- `basePath: ""` — better-auth's default `/api/auth` prefix would put OIDC
  discovery at `/api/auth/.well-known/openid-configuration`. With `basePath:
  ""` the endpoints live at the OIDC-standard root paths, so the issuer URL is
  directly discoverable by Supabase.
- `oidcProvider({ useJWTPlugin: true })` — without this the id_token is
  HS256-signed with the client secret (the plugin default), which Supabase
  cannot verify against the RSA JWKS. With it, the id_token is RS256 with a
  `kid` matching the JWKS.
- The JWT plugin's `jwks` model stores the key rows (encrypted by default);
  the lab disables encryption only so the test suite can sign crafted
  negative tokens with the real key. Production keeps encryption on.
- id_token `aud` is the **registered client id** (OIDC spec); the app-level
  audience (`velure-api`) is configured on the JWT plugin for the app's own
  session JWTs.
- `sub` is the better-auth user id — exactly the value Supabase Auth will
  place in its own JWT `sub` after the OIDC exchange, which is what
  `app.current_user_id()` (`auth.jwt() ->> 'sub'`) returns and what the app
  stores in `owner_id`/`user_id`.

### 1. Schema migration (written, validated locally)

`supabase/migrations/20260817012325_phase_a9_better_auth_schema.sql` creates
the `better_auth` schema with the 8 tables + indexes better-auth 1.4.9's
Kysely adapter generates for the jwt + oidcProvider plugins (`user`,
`session`, `account`, `verification`, `jwks`, `oauthApplication`,
`oauthAccessToken`, `oauthConsent`). Key points:

- **Every identifier is double-quoted** (`"emailVerified"`, `"createdAt"`, ...)
  — Postgres folds unquoted camelCase to lowercase, and better-auth queries
  the quoted names. Unquoted columns fail at first signup (`column
  "emailVerified" ... does not exist`).
- ids are `text` (better-auth generated), `redirectUrls`/`metadata`/`scopes`
  are comma-/JSON-serialized `text`, `createdAt`/`updatedAt` default to
  `CURRENT_TIMESTAMP`, all FKs `ON DELETE CASCADE`.
- `anon`/`authenticated`/`service_role` are revoked from the schema and all
  tables — the tables are reachable only by the issuer's direct Postgres
  connection (project owner role with search_path pinned to `better_auth`);
  they are never exposed through PostgREST (`public` is the only exposed
  schema) and have no RLS policies (server-side-only by isolation).
- The DDL was produced by compiling better-auth's own `getMigrations()`
  output for the exact plugin config, schema-qualified to `better_auth` —
  not guessed from docs.

### 2. Production issuer server (`production-issuer.mjs`)

Standalone HTTP server around better-auth with a raw `pg.Pool` as
`database` (better-auth auto-detects Postgres and uses its internal Kysely
adapter). Env: `ISSUER_URL`, `DATABASE_URL` (velure-cc direct connection),
`BETTER_AUTH_SECRET` (>=32 chars; also encrypts jwks private keys),
`PORT`, `CLIENT_ID`, `CLIENT_SECRET`, `REDIRECT_URIS`, optional
`RESEND_API_KEY`/`RESEND_FROM` for verification emails.

- search_path is pinned to `better_auth` on the pool, so better-auth's
  unqualified table names never touch `public`.
- `requireEmailVerification: true` + Resend `sendVerificationEmail` — GoTrue
  rejects OIDC sign-ins with unverified email
  (`provider_email_needs_verification`), so real verification is required;
  the harness's `__dev/verify-email` route is NOT ported.
- private key encryption stays ON (the harness disabled it only so the
  runbook could re-verify id_token signatures offline).
- Dependencies: `pg` (runtime), `kysely@^0.28.5` + `drizzle-orm` (dev, used
  by the schema generator below).

#### Three production-shape bugs the live Postgres run caught (all fixed)

The memory-adapter harness could never have caught these — all three are
Postgres/config gaps, not logic gaps:

1. **`loginPage` is a REQUIRED `OIDCOptions` field.** With no session,
   better-auth redirects to `${options.loginPage}?<query>` — unset, it emits
   the literal URL `"undefined?..."`, which kills the flow. The harness
   never hit this branch because signup auto-signed-in (no email
   verification); the production issuer requires verification and does not
   auto-sign-in, so every real browser hits it. Fix: `loginPage:
   `${ISSUER_URL}/sign-in`` (the app must serve a sign-in page there).
2. **Trusted clients + Postgres FK = token-endpoint crash (better-auth
   issues #4749 / #6649).** `oauthAccessToken.clientId` has an FK to
   `oauthApplication`, but config-level `trustedClients` are never persisted
   as rows, so every code exchange died with `23503` (the memory adapter has
   no FK enforcement). Fix (maintainer-suggested): the issuer seeds/upserts
   the trusted client into `oauthApplication` at startup (id = randomUUID,
   `redirectUrls` comma-joined — that is how `getClient` splits them).
3. **The client secret must match on BOTH sides.** GoTrue sends the
   provider's registered `client_secret` at the token endpoint; the issuer
   validates it against its own trusted-client config. A mismatch yields
   `invalid_client` (and a follow-on `invalid_grant`). Fix: run the issuer
   and the registration/suite with the same `CLIENT_SECRET`.

Also fixed along the way: the issuer's `jwks` key was encrypted with a
*different* secret by the first launch — a pre-production key, so cleared
(`delete from better_auth."jwks"`) and regenerated under the current
secret. **Operational rule: BETTER_AUTH_SECRET must never change after the
first boot, or stored keys can't decrypt.** The suite's cleanup now guards
empty IN-lists and deletes `better_auth` users it created.

Ran the actual A9 activation path against `velure-cc` with a standalone

**The load-bearing result is negative:** the Supabase JWT `sub` is a
**GoTrue-minted UUID**, not the better-auth user id:

- Supabase JWT `sub` = `a247c4b7-...` (GoTrue user id)
- `auth.identities.provider_id` = the **better-auth user id** (recoverable)
- `auth.identities.identity_data.sub` = the better-auth user id

So `auth.jwt()->>'sub'` (what `app.current_user_id()` reads) will **not**
equal `owner_id` for OIDC-signed-in users. **Resolved (2026-08-15):**
`supabase/migrations/20260815223943_phase_a9_identity_sub_claim_hook.sql`
creates `public.custom_access_token_hook(jsonb)` (the Supabase custom access
token hook; runs at token issuance, security definer, granted only to
`supabase_auth_admin`) which copies `auth.identities.provider_id` for
`custom:velure` into the JWT as the `velure_user_id` claim, and updates
`app.current_user_id()` to `coalesce(auth.jwt()->>'velure_user_id',
auth.jwt()->>'sub')`. Validated locally: full 19-migration history applies on
Postgres 17, the hook injects the claim only for OIDC identities, the helper
falls back to `sub` for password flow, and the A9 RLS suite (now incl. an
OIDC sub-claim scenario) stays green.

**Applied to `velure-cc` (2026-08-15) and verified live.** The function is
live with the right ACL (`postgres`, `service_role`, `supabase_auth_admin`
only; anon/authenticated revoked). A second live exchange re-ran with the
hook in place: the full flow still works, but the minted JWT had **no
`velure_user_id` claim** — creating the function is not enough; the hook must

**Identity continuity gate (`identity-continuity.mjs`, CI-wired 2026-08-17).**
The pre-flip proof that a real user's existing rows resolve after the flip —
built from the live proof above (oldest real owner provisioned at the issuer
with the SAME id, signed in via the real `/sign-in/email`, GoTrue authorize,
minted JWT's `velure_user_id` must equal the stored `owner_id`, RLS must
return their real workspace + membership + active row). Safety: the
provisioned user carries a SYNTHETIC email (never the owner's), and cleanup
runs in a `finally` block keyed on it — a mid-flow tunnel failure can never
leave the issuer user, GoTrue user, or provider behind. Two modes:

```bash
pnpm run guard:identity-continuity                # full live check
pnpm run guard:identity-continuity --check-data   # remote invariants (linked project)
pnpm run guard:identity-continuity --local        # local invariants (SUPABASE_DB_URL / --db-url)
pnpm run guard:identity-continuity --self-test    # offline predicate self-test
```

- `--check-data` / `--local`: scan every user-bearing public column and
  fail if any row is not a Convex-era id or is an orphan (no workspace
  owner). This is the regression guard for "nothing may write a GoTrue
  `sub` into owner_id/user_id". The two modes run the SAME shared check
  logic — `--check-data` against the linked project via the management
  API, `--local` against a Postgres reachable at `SUPABASE_DB_URL` /
  `--db-url` (psql, or `docker run postgres:17 psql` when psql is
  absent), mirroring `guard-anon-privileges --local` so CI can run it
  unconditionally in the same job.
- CI (`.github/workflows/supabase-rls-guards.yml`): the identity check now
  sits ALONGSIDE the anon-privileges guard in the same job — the
  migration-applied Postgres runs `--local` (a migration that seeds a
  non-k5 id fails CI immediately), then an inject-and-bite self-test
