# Fix intermittent sign-in 1101 on the Worker runtime

Status: done
Task: fix the production defect where `POST /api/auth/sign-in/email` failed with
Cloudflare error 1101 (HTTP 500) for roughly half of all requests. The dead-pool
bug (1101) was found, fixed, deployed, and is verified. Doing so uncovered a
second, platform-level failure on the same route (1102, `exceededCpu`); that one
was root-caused, tested to be unfixable within the free CPU budget, and resolved
by moving the app to a Node host. See "Outcome" at the end.

## Goal

Make email/password sign-in succeed consistently on Cloudflare, without weakening
any tenancy, credential, or session guarantee.

## Live defect (verified, not assumed)

- `POST /api/auth/sign-in/email` on `https://velure-f2c.pages.dev` returned
  Cloudflare **error 1101** ("Worker threw a JavaScript exception") with an
  otherwise-valid payload. Ten sequential calls: `500 200 500 200 500 500 200
  200 500 200`.
- It reproduced on the **previous** deployment (`f5d3e82b`), so it predated the
  T8/UI work, and it still failed with 3 s spacing, so it was not request
  concurrency.
- Reads were unaffected: `GET /api/auth/get-session` without a cookie returned
  200 six times out of six (that path never queries the database).
- Local dev was clean, which pointed at the Worker runtime.
- Reproduced locally in the real runtime (`npx wrangler pages dev dist`, built
  `dist`, real `.env`): `200 500 200 500 200 500 200 500 200 500`, and the Worker
  logged
  `Uncaught Error: The Workers runtime canceled this request because it detected
  that your Worker's code had hung and would never generate a response.`
- Successes took 1.2-1.9 s (a real round trip); failures took 12-28 ms.
- An **unknown email** — which never verifies a password — failed the same way
  (alternating `401 500 401 500 ...`), which **refutes** the initial scrypt
  hypothesis. (Measured anyway: `@noble/hashes` scrypt at better-auth's cost is
  ~212 ms CPU and 32 MB per verify, and both 1.8.0 and 2.2.0 ship
  `export const nextTick = async () => { };`.)
- Root cause: `src/lib/auth.ts` built a **module-scope `pg.Pool`**. A Worker
  invocation owns its sockets; when the response is returned the runtime cancels
  outstanding I/O. The pooled client survived at module scope, so the next
  invocation was handed a dead socket and its query never settled.

- No Cloudflare log access was available (`wrangler whoami` fails with "Failed to

- The 5 existing scrypt credential hashes must not be invalidated: the password

## Implementation requirements

1. No connection may outlive the Worker invocation that opened it.
2. Correctness first: an unsupported caller (no request scope) still gets a fresh
   connection per acquisition, so behaviour can never be silently shared.
3. One auth request reuses a single connection, because a fresh connection to
   Supabase's pooler measured ~0.6-0.9 s from Node and made login 4-8 s when each
   query opened its own.
4. Do not touch password hashing, session shape, cookies, numbering, money, or
   issued-invoice behaviour.

## Post-deploy finding (2026-11-01): the 1101 is gone, but the edge still fails

`c541839` was deployed (`47c0d657`, alias `velure-f2c.pages.dev`). The 1101
"hung Worker" failure is gone. Sign-in on the edge now fails with a **different**
error: `503` / Cloudflare **1102**, outcome `exceededCpu`, exception
`Worker exceeded CPU time limit.`

### What was measured

- `wrangler pages deployment tail <id> --project-name velure --format json`
  reports `"outcome":"exceededCpu"`, `"exceptions":[{"message":"Worker exceeded
  CPU time limit."}]`, `executionModel: "stateless"`.
- Same tail, the **old** deployment `c0674e02` shows **both** failure modes:
  `500`/`exception` ("canceled this request because it detected that your
  Worker's code had hung", cpu 3-8 ms, wall 4-9 ms) **and** `503`/`exceededCpu`
  (cpu 10-102 ms, wall 449-1409 ms). Its successful requests cost
  **cpuTime 326-335 ms**.
- So the CPU limit is **not** specific to this change: both builds exceed it.
  c541839 makes it *more* visible because requests now reach the password step
  instead of dying on a dead socket first.
- `GET /api/auth/get-session` (no DB access) is 15/15 `200` on both builds.
- Every DB-touching auth request fails: 30/30 on `velure-f2c.pages.dev` (503)
  and 30/30 on `c0674e02` (500), including **unknown email**, which never runs
  scrypt.
- Local `wrangler pages dev` (no CPU cap) is 5/5 `200` for the same request, so
  the code, credentials, and network path to Postgres are all good.
- Supabase is healthy independently: `select now(), count(*) from
  better_auth."user"` works, and Node reaches the pooler in ~600 ms with a
  burst of 10 concurrent connections.
- After a 150 s quiet window the first sign-in still fails (`get-session=200`
  immediately before it, `signin=503`).

### Root cause

The deployment runs with `usage_model: "bundled"` (Cloudflare API,
`GET /accounts/{id}/pages/projects/velure/deployments/{id}`) and
`compatibility_flags: ["nodejs_compat"]`. Cloudflare's documented CPU budget is
far below what this auth path needs:

- Workers Free: **10 ms CPU per HTTP request**.
- Legacy Bundled: **50 ms CPU per HTTP request**.
- Both allow only *infrequent* overruns, and Cloudflare terminates an isolate
  once it hits the limit consistently
  (https://developers.cloudflare.com/workers/platform/limits/#cpu-time).

better-auth verifies passwords with `@noble/hashes` scrypt at
`N=16384, r=16, p=1, dkLen=64`
(`better-auth/dist/crypto/password.mjs`), measured here at **237 ms CPU**
(Node, same parameters). That is 5-24x the per-request budget, for every
sign-in, independent of traffic.

Reducing the cost was tested and does not close the gap: a native
`node:crypto` scrypt over the same parameters is **142 ms CPU**, still over
budget, and it produces **byte-identical** keys (verified against the live
`qa-responsive@velure.test` hash and a fresh hash), so it would not break the
five stored credentials — but it is not a fix.

### Consequence

This is not a code defect that can be fixed inside the Worker. It needs a
decision about the execution environment (raise the CPU limit / move the auth
path off the CPU-limited runtime). Recorded in `docs/DECISIONS.md`.

## Outcome (2026-11-01)

Both agreed experiments were run, and the decision from them is "move to a Node
host" (`prompts/vps-node-deployment-2026-11.md`).

**Option 2 — a free CPU reduction. Tested, works, but does not fit the budget.**
A native `node:crypto` scrypt was implemented and verified byte-identical to
better-auth's `@noble/hashes` scrypt, so all five stored credentials still
verified. Measured on the edge it was a real improvement but not a fix:

- fair alternating A/B on the same request, 2 s apart: noble `47c0d657` **0/15**,
  native `3c174cd6` **9/15** (0% -> 60%).
- CPU split, from `wrangler pages deployment tail`: `GET /api/auth/get-session`
  with a real session cookie (DB session lookup, no scrypt) = **15-20 ms**;
  sign-in = **131-146 ms**.
- The scrypt cost is irreducible: better-auth calls `password.hash(password)`
  even when the account does not exist (`dist/api/routes/sign-in.mjs:196/202/208`,
  a timing equalizer), so every attempt pays one scrypt, and the parameters are
  fixed by the stored `${salt}:${keyHex}` format.
- 142 ms (native) against a 10-50 ms budget cannot be closed by optimisation.

The experiment was reverted at the user's direction. The Cloudflare path stays in
the repository and keeps the Worker-safe connection strategy as its default.

**Option 3 — run off the Workers CPU cap. Works.** `pnpm build` emits a
self-contained Nitro `node-server` bundle (`.output`); on Node it signs in with
`200` and no CPU ceiling. Deployment artifacts are in `deploy/`.

### What shipped

- `src/server/auth-database.ts` now selects its connection strategy from
  `AUTH_DB_MODE`: `pool` = a real `pg.Pool` (Node/VPS), anything else = the
  Worker-safe invocation-scoped client. On Node with `pool`, an authenticated
  request went from **1.0-2.4 s to 0.4-0.7 s** and sign-in from 1.6-2.0 s to
  ~0.7 s (measured against the same Supabase pooler).
- Auth hardening (see the deployment prompt for the full list): explicit rate
  limits, a pinned `x-forwarded-for` trust boundary, a 12-character password
  minimum with a bounded maximum, session revocation on password reset, a
  32-character minimum for `BETTER_AUTH_SECRET`, and an email-redacting logger.
- `deploy/velure.service`, `deploy/velure.env.example`, `deploy/nginx-velure.conf`,
  `deploy/README.md`.
