# Fix intermittent sign-in 1101 on the Worker runtime

Status: done
Task: fix the production defect where `POST /api/auth/sign-in/email` returned
Cloudflare error 1101 (HTTP 500) for roughly half of all requests.

## Goal

Make email/password sign-in succeed consistently on Cloudflare, without weakening
any tenancy, credential, or session guarantee.

## Live defect (verified, not assumed)

- `POST /api/auth/sign-in/email` on `https://velure-f2c.pages.dev` returned
  Cloudflare **error 1101** ("Worker threw a JavaScript exception") with an
  otherwise-valid payload. Ten sequential calls: `500 200 500 200 500 500 200
  200 500 200`.
- It reproduced on the **previous** deployment (`f5d3e82b`), so it predated the
  T8/UI work, and it still failed with 3 s spacing, so it was not request
  concurrency.
- Reads were unaffected: `GET /api/auth/get-session` without a cookie returned
  200 six times out of six (that path never queries the database).
- Local dev was clean, which pointed at the Worker runtime.
- Reproduced locally in the real runtime (`npx wrangler pages dev dist`, built
  `dist`, real `.env`): `200 500 200 500 200 500 200 500 200 500`, and the Worker
  logged
  `Uncaught Error: The Workers runtime canceled this request because it detected
  that your Worker's code had hung and would never generate a response.`
- Successes took 1.2-1.9 s (a real round trip); failures took 12-28 ms.
- An **unknown email** — which never verifies a password — failed the same way
  (alternating `401 500 401 500 ...`), which **refutes** the initial scrypt
  hypothesis. (Measured anyway: `@noble/hashes` scrypt at better-auth's cost is
  ~212 ms CPU and 32 MB per verify, and both 1.8.0 and 2.2.0 ship
  `export const nextTick = async () => { };`.)
- Root cause: `src/lib/auth.ts` built a **module-scope `pg.Pool`**. A Worker
  invocation owns its sockets; when the response is returned the runtime cancels
  outstanding I/O. The pooled client survived at module scope, so the next
  invocation was handed a dead socket and its query never settled.

## Decisions / assumptions (confirmed with user)

- **User answer 2026-10-31:** chose **"Fix sign-in first (Recommended)"** over
  proceeding with the TIN 10-12 digit migration, because this affects real users.
- No Cloudflare log access was available (`wrangler whoami` fails with "Failed to
  automatically retrieve account IDs"), so the exception was obtained from the
  local `wrangler pages dev` Worker runtime instead of a deployment tail.
- The 5 existing scrypt credential hashes must not be invalidated: the password
  hashing path is **not touched**.
- Connection handling is a server-only concern: no schema, route contract,
  cookie, or session-shape change.

## Implementation requirements

1. No connection may outlive the Worker invocation that opened it.
2. Correctness first: an unsupported caller (no request scope) still gets a fresh
   connection per acquisition, so behaviour can never be silently shared.
3. One auth request reuses a single connection, because a fresh connection to
   Supabase's pooler measured ~0.6-0.9 s from Node and made login 4-8 s when each
   query opened its own.
4. Do not touch password hashing, session shape, cookies, numbering, money, or
   issued-invoice behaviour.

## Scope changes (append-only)

- 2026-10-31: Prompt created. First attempt used a fresh `pg.Client` per
  acquisition and closed it on release. That fixed correctness (10/10 200) but a
  sign-in took 3.7-8.0 s, because each Kysely query opened a new connection.
- 2026-10-31: Added `withAuthConnection` (AsyncLocalStorage) so all queries for
  one auth request share one connection, closed once when the request finishes.
  Sign-in returned to 1.5-2.2 s with the failures still gone.
