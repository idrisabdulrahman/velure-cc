# Widen the Nigerian TIN format to 10–12 digits

Status: done
Task ID: tin-length-10-12-2026-11

## Goal

The B1/B2 TIN format rule currently rejects anything that is not exactly 10
digits. NRS guidance and mainstream accounting tools (Zoho Books) describe a
10–12 digit TIN, so the 10-digit-only rule risks flagging valid customer TINs.
Widen the rule to `^\d{10,12}$` in the one canonical validator, propagate the
same range to the UI hints and the SQL mirrors through a NEW reversible
migration, and keep every existing severity decision intact:

- `tin_required` and `tin_placeholder` stay blocking.
- `tin_format` stays a **warning** (records `needs_review`) until NRS confirms
  the exact structure.

This is not a Midday parity port. Classification: N/A (local compliance rule
change). No Midday source is ported.

  save and self-heal. There is no server-side regex to change beyond the SQL
  backfills.

## Implementation requirements

1. One canonical rule: `NIGERIA_TIN_MIN_DIGITS = 10`,
   `NIGERIA_TIN_MAX_DIGITS = 12`, `NIGERIA_TIN_PATTERN = /^\d{10,12}$/`. Remove
   `NIGERIA_TIN_DIGITS`; update every consumer.
2. The placeholder rule (`isAllSameDigit` / explicit list) is unchanged and still
   blocking. A 10–12 digit all-same value (e.g. `11111111111`) is a placeholder,
   not a valid TIN.
3. UI clamps and hints derive from the shared constants so they cannot drift.
4. The new migration must be: flag-only (writes only
   `supplier_profile_*` / `buyer_profile_*`), idempotent (`is distinct from`),
   scoped to rows already flagged `tin_format`, and carry the full widened rule
   (`^[0-9]{10,12}$`, the placeholder list, `^(.)\1{9,11}$`) in the app's
   format-before-placeholder order. Reversal is a comment block.
5. The migration file name must NOT end `_supplier_profile_validation_flags.sql`
   or `_einvoice_b2_buyer_profile_flags.sql` (the historic parity tests read the
   last matching file).
6. Do not modify the two applied migrations, `ProductStrategy.md`,
   `Architecture.md`, or `migration-plan.md`.
