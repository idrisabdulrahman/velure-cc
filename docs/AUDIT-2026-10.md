## 1. Scheduler

**Verdict: Confirmed.** There is no scheduler on the Cloudflare Pages deploy.
Four background jobs exist as HTTP endpoints that nobody calls on a schedule.

- `src/routes/api/invoice/scheduled.ts:2-15` — scheduled invoice email dispatch,
  protected by `INVOICE_SCHEDULER_SECRET`.
- `src/routes/api/invoice/submissions/scheduled.ts:5` — comment: *"Internal cron
  trigger; deployers must wire it to a scheduler separately."*
- `src/routes/api/payments/paystack/reconcile.ts:5-9` — comment: *"Deployers
  must wire it to a scheduler (cron) separately, exactly like the invoice
  submission/email schedulers."*
- `src/server/data/reminders.ts:23` — *"Slack dispatch and cron bookkeeping
  remain separate infrastructure work."*
- `src/server/data/invoices.ts:54` — a surviving note that cron *"stays on
  Convex"*.

What actually invokes the work today:

| Job | Code | Only trigger found |
| --- | --- | --- |
| Reminder batch scan | `runReminderBatch` `src/server/data/reminders.ts:732` | Manual **"Scan invoices"** button, `src/routes/settings.collections.tsx:454` |
| Reminder email drain | `sendQueuedEmails` `src/server/data/reminders.ts:799` | Manual **"Send queue"** button via `POST /api/reminders/send-queue` (`src/routes/settings.collections.tsx:481`) |
| Scheduled invoice emails | `dispatchScheduledInvoiceEmails` `src/server/invoice-mailer.ts:53` | `POST /api/invoice/scheduled` only (no caller) |
| Paystack pending-charge reconciliation | `reconcilePendingPaystackCharges` | `POST /api/payments/paystack/reconcile` only (no caller) |
| E-invoice sandbox submissions | `dispatchDueInvoiceSubmissions` | `POST /api/invoice/submissions/scheduled` only (no caller) |

Deployment target confirms it: `package.json` deploys with
`wrangler pages deploy` (Cloudflare **Pages**), which has no Cron Triggers.
There is no `wrangler.toml`, and no `pg_cron` / `pg_net` usage anywhere in
`supabase/migrations/`.

Live database corroboration:

- `job_runs`: 10,893 rows, last `started_at` **2026-08-15**, all from **1**
  workspace.
- `reminder_runs`: 80,851 rows, last `run_date` **2026-08-15**, all `completed`,
  1 workspace.

No automation has run in roughly 2.5 months, and the rows that exist are
test/demo artifacts, not production scheduling.

## 2. Mock e-invoicing artifacts

**Verdict: Refuted** for the stated risk (a realistic-looking frozen IRN/QR on a
customer document). The artifacts are unmistakably fake and are only rendered
with an explicit stamp.

The mock format is deliberately non-realistic:

- `src/features/einvoicing/provider-adapter.ts:112-118` — IRN is
  `MOCK-IRN-<hash>`, QR payload is
  `MOCK-SANDBOX|NOT-NRS-CLEARED|IRN=...|REFERENCE=...`.

Render paths enumerated:

| Path | File | Mock artifact rendered? |
| --- | --- | --- |
| Invoice PDF | `src/server/pdf.ts:68-76` | Only when `environment==="sandbox"`, `mockIrn.startsWith("MOCK-IRN-")`, `qrCodePayload.startsWith("MOCK-SANDBOX\|NOT-NRS-CLEARED\|")`; renders header **"MOCK SANDBOX — NOT NRS CLEARED"** plus the values |
| PDF template | `src/lib/midday-invoice/templates/pdf/index.tsx:175-183` | Label + `Mock IRN:` + QR, gated on `mockClearance` |
| Public page | `src/routes/i.$token.tsx` (renders `HtmlTemplate`) | **No** — no fiscalization/mock rendering in `src/lib/midday-invoice/templates/html/**` |
| Public JSON payload | `src/server/data/invoices.ts:819-844` `mapPublicInvoice` | `fiscalization` is included **only** if every mock prefix matches, else `{status:"not_configured"}` |
| Email | `src/server/invoice-mailer.ts:30-43` | Body has no IRN; attaches the PDF, so it inherits the stamped PDF |
| Compliance exports | `src/server/data/compliance.ts` | **No** fiscalization/mock columns |

Pinned by test: `src/server/pdf.mock-clearance.test.ts:45-75` asserts artifacts
are **hidden** before explicit mock clearance and **labelled** after.

Residual (minor, not a blocker): a mock-cleared invoice does put the
`MOCK-IRN-...` string into the public `/api/invoice/public/$token` JSON payload.
It is not rendered anywhere the buyer sees, but it is shipped to the browser.
Whether to strip it from the public payload is a small hardening decision.

## 3. RLS and service role

**Verdict: Confirmed and already documented honestly.** The server talks to
Postgres with the **service-role key**, which bypasses RLS. App-layer workspace
scoping is the load-bearing control; RLS is a second layer for direct browser
PostgREST access and for `rls-only` functions.

- `src/server/supabase.ts:6-26` — `getSupabaseAdminClient()` requires
  `SUPABASE_SERVICE_ROLE_KEY` (or legacy `SUPABASE_SECRET_KEY`).
- `docs/e-invoicing/tenant-isolation.md:9-24` — states directly that every probe
  passes against a **no-RLS** client, so *"the app-layer filters alone are
  load-bearing. RLS is proven as defense-in-depth."*
- Identity is **Better Auth**, not Supabase Auth. Live schemas: `auth.users`,
  `auth.sessions`, and `better_auth.{user,session,account}`. The bridge is
  migration `20260815223943_phase_a9_identity_sub_claim_hook.sql`.
- The guard `src/server/data/tenant-isolation-coverage.test.ts` forces every
  data export and `src/routes/api/**` handler to declare its isolation
  mechanism.
- Stated gap (`tenant-isolation.md:62-71`): the live RLS matrix
  (`src/server/data/tenant-isolation.live.test.ts`, `pnpm
  test:wp3-tenant-isolation-live`, 25 tables) requires a linked project and was
  **not executed** in the build environment.

The landing **Security** section (`src/routes/index.lazy.tsx:79-102, 559-611`)
and `/settings/security` make **no** RLS or encryption claim, so the
customer-facing copy already matches what is enforced.

## 4. Midday license

**Verdict: Confirmed. Material.** The parity source is **AGPL-3.0**.
**Stop and ask before shipping** (see T3 / `docs/DECISIONS.md`).

- `/home/asys/JS-TS/apps/projects/midday-main/LICENSE` — *"GNU AFFERO GENERAL
  PUBLIC LICENSE Version 3"*, *"Copyright (c) 2023-present Midday Labs AB."*
- Derived code in Velure: `src/lib/midday-invoice/**` (PDF + HTML templates,
  `token/index.ts`, `utils/*`, `types.ts`) and the adapter
  `src/features/invoices/midday-adapter.ts`.
- The Velure repo has **no** `LICENSE` or `NOTICE` file (`find` across the repo
  root: none).
- Plain-language obligation: AGPL-3.0 §13 requires that users interacting with a
  modified version **over a network** be offered the corresponding source. A
  closed-source paid SaaS is the hard case. This is a decision, not a code fix.
